## Последнее изменение интерфейса

Отдельные карточки между картой и Markdown-разделом удалены.

После карты сразу отображается раскрытый раздел:

**«Исходные описания из Markdown-файлов»**

Технические блоки вида:

- «Данные карты: адреса и переходы к точкам (школа)»;
- «Данные карты: адреса и переходы к точкам (детский сад)»

удалены.

Адреса и обратные ссылки теперь добавляются непосредственно к соответствующим описаниям исходных Markdown-файлов. Для каждого объекта выводятся:

- тип объекта;
- адрес;
- ссылка `↗ Показать на карте`;
- связанная школа для детского сада;
- примечание;
- источник адреса, если он указан.

Ссылка `↗ Показать на карте` прокручивает страницу к карте, центрирует её на объекте, увеличивает масштаб и открывает нужный popup.

## Источники данных

Редакционные тексты:

- `Лучшие школы Москвы.md`;
- `Лучшие детские сады Москвы.md`.

Картографический слой:

- `places.json` — единый актуальный источник объектов карты;
- старый `schools.geojson` сохранён для истории/отката, но не определяет текущий состав сайта.

## Структура объектов

Каждый корпус или отделение представлен отдельным объектом в `places.json` с уникальным `id`, координатами и адресом.

Связанные объекты объединяются полями:

- `group` — организация/семейство объектов;
- `associated_school` — школа, к которой относится детский сад;
- `entity` — `school` или `kindergarten`;
- `kind` — `green`, `blue` или `red`;
- `source` — источник адреса;
- `notes` — дополнительное пояснение.

Школа и детский сад не сливаются в одну точку, если это разные здания.

## Цветовая логика

- зелёный — детские сады и связанные с ними школы;
- синий — школы с приёмом с 1 класса;
- красный — остальные школы из выбранного списка.

Фильтр карты имеет четыре режима:

1. только детские сады и связанные школы;
2. школы с 1 класса;
3. объединённый режим;
4. все объекты.

## Извлечённые уроки

1. Старый GeoJSON нельзя использовать как источник полного состава, если исследование обновилось.
2. Организация, корпус, школа и детский сад — отдельные сущности.
3. Связь между сущностями нужно хранить данными (`group`, `associated_school`), а не угадывать по названию в интерфейсе.
4. Обратную ссылку на карту нужно строить по стабильному `id`, а не по тексту адреса.
5. Publishing branch нужно проверять отдельно: обновление `main` не означает автоматическое обновление GitHub Pages, если Pages настроен на `gh-pages`.
6. После push нужно проверять опубликованные `index.html`, `app.js` и `places.json` через GitHub Raw или GitHub Pages, а не только локальный Git.
7. При изменении адресов сначала проверять официальную страницу контактов, затем менять `places.json` и координаты.
8. Исходный Markdown должен оставаться редакционным текстом; служебные адреса и ссылки добавляются рядом с соответствующим описанием динамически.

## Быстрое обновление

1. Проверить официальный адрес/корпус.
2. Изменить объект в `places.json`.
3. При новой организации добавить уникальный объект с `id`, `entity`, `kind`, `group`, адресом и координатами.
4. Запустить проверки выше.
5. Проверить сайт локально через HTTP:

```bash
python -m http.server 8000
```

6. Закоммитить изменения в `main`.
7. Пересобрать содержимое `gh-pages` из `main`.
8. Проверить live-версию через `raw.githubusercontent.com` и GitHub Pages.

Не редактировать адреса напрямую в `index.html`: они должны оставаться в `places.json`.
